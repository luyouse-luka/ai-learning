## 关键概念笔记（ly 自己写，教练批注）

> 下面是 ly 原文，**不改动**。`💬 教练` 是批注。

### 接 Week 1

### week1 中的 deepseek-chat 弃用

> 💬 **教练**：官方文档原话是 `deepseek-chat` / `deepseek-reasoner` 于 **2026-07-24 弃用**，现在是 `deepseek-v4-flash` 的别名。**弃用 ≠ 立刻停用**，多半还能跑一段时间。ly 选择暂不处理（8 处硬编码散在 week1 各脚本里）。
> **哪天脚本突然报「模型不存在」，第一个怀疑对象就是它。**
> 附带的教训：**模型名写死在 8 个文件 = 8 处要改**。写进 `.env` 或定义成常量，就只改 1 处。

### usage 三个字段
    -usage.prompt_tokens        输入 token 数（你发出去的：system + 历史 + 本轮 user）
    -usage.completion_tokens    输出 token 数（模型吐回来的）
    -usage.total_tokens         两者之和

> 💬 **教练**：记法——**prompt = 你提的（输入）**，**completion = 它补的（输出）**。这两个词在整个 LLM 生态通用，不只 DeepSeek。

### token成本算法
    比如deepseek 输入 1￥/百万 输出2￥/百万
    则应该 prompt_tokens / 百万 * 1 + completion_tokens / 百万 * 2

> 💬 **教练**：**这次形状写对了**，输入输出分开算、单价乘上去。这是你连错两轮之后终于拿下的一条，记死它：
> **成本 = token 数 ÷ 1,000,000 × 单价**
> `÷ 1,000,000` 是把「多少个 token」换算成「多少个百万」，`× 单价` 是每百万收多少。**先换单位，再乘价格。**
>
> 补一条反直觉的：Week 1 默写题里输入 1200 token / 输出 800 token，**输出更少但更贵**（0.0016 > 0.0012），因为输出单价是输入的 2 倍。所以「钱主要花在 input 上」**只在长文总结这类「喂得多、吐得少」的任务里成立**。

### Week 2 前瞻
    1.长文总结的三层矛盾
        1-1: 输入内容限制，当输入内容过大，比如50万token，模型无法处理，由于物理限制，无法输入进去，只能拆
        1-2: 即使50万token长的文本能够输入进去，但是上下文过长，模型处理起来会产生幻觉，可能会忘记中间部分，专业名词叫"lost in the middle"，开头结尾记得很清楚，但中间模糊
        1-3: 当上下文过长时，处理起来会耗费过量的token，长文本任务成本几乎由你喂进去多少决定的

> 💬 **教练**：三层都抓住了。补一句关键的现实：**DeepSeek 现在是 1M 窗口，第 1-1 层的硬墙已经被推得很远**——50 万 token 其实塞得进去。
> **但 1-2 和 1-3 一点没变。** 所以分段策略照学，只是理由从「塞不下」变成了**「塞得下，但不该那么塞」**。

    2. 三种策略优势
        2-1： Stuff 能一次性输入进去最好，上下文最完整，优先选择
        2-2： Map-Reduce 分块处理总结，然后在一起总结处理
              优点：并行，快，无上限，缺点：可能会丢失某些东西，因为处理每块总结的不一定完整且符合总体
        2-3： Reine 迭代精炼
              每处理一块就总结，之后的每处理一块都进行修改调整
              优点： 上下文连贯，慢，处理到最后一些内容仍可能会丢失

> 💬 **教练**：三条理解都对，两处要修：
> 1. **拼写**：`Reine` → **`Refine`**（精炼、提纯）
> 2. **2-3 把「慢」写进了优点栏**。分清楚：
>    - **优点**：上下文连贯，跨章节的线索能保住
>    - **缺点**：只能**串行**（第 2 步必须等第 1 步）所以慢；而且越读到后面，前面的细节被稀释得越厉害
>
> Map-Reduce 的缺点再说准一点：**没有任何一次调用读过全文**。第 3 章埋的伏笔在第 9 章回收，这种跨块的线索必然丢。
>
> **选型直觉**：各章相对独立（论文/报告/一堆邮件）→ Map-Reduce；前后强关联（小说/案情/时间线）→ Refine；塞得下 → 永远先试 Stuff。

    3. deepseek 上下文窗口： 1,000,000 tokens（1M），最大输出 384K tokens。

> 💬 **教练**：对。**别背这个数字**——模型规格会变，要养成的是「去官方文档查一次」这个动作本身。今天就是活例子：如果我凭记忆给你，会给一个过期的数，而且完全不会发现模型名要弃用。

## Day 1 实测数据（`attention.pdf`）

```
字符数:        39597
估算 token:    11879.1      （39597 × 0.3）
喂一次的成本:  $0.001663    （11879.1 ÷ 1,000,000 × 0.14）
```

**结论**：11879 ÷ 1,000,000 = **1.2%**，这篇论文只占满 1M 窗口的 1.2%。
要塞满窗口得同时放 **84 篇**这样的论文。**所以对它，最佳策略就是 Stuff——直接一次塞完。**

## Day 2 实测数据（`attention.pdf` 全文 Stuff 总结）

| 项目 | 数值 |
|---|---|
| 输入字符数 | 39612（比 Day 1 多 15，因为页间加了 `\n`） |
| 估算输入 token（×0.3） | 11883.6 |
| **真实 `prompt_tokens`** | **10138** |
| **估算误差率** | **+17.22%**（估高了 → 安全方向） |
| **真实输入比例** | **0.256** token/字符 |
| `completion_tokens` | 364（= reasoning **175** + 正式回答 **189**） |
| 正式回答字符数 | 342 |
| **正式回答比例** | **0.55** token/字符 |
| 一次总成本 | $0.00152（每 1000 次 ≈ $1.52） |
| `finish_reason` | `stop`（没被截断） |

> ⚠️ **`deepseek-v4-flash` 是推理模型**：回答前先「想」一段（`message.reasoning_content`），
> 这段也计入 `completion_tokens`，**也按输出价计费**。这次推理占了 **48%**。
> - `max_tokens` 卡的是 **reasoning + 正式回答的总和**，所以余量要留得比普通模型宽
> - 推理长度**不可控**（题越难想越久），你只控制得了正式回答的长度
> - 极端情况：`max_tokens=12` 时推理就用光了，`content` 返回**空字符串**，钱照花

## Day 3 速查（教练给的硬知识，2026-08-04）

> 主题：**把脚本变成服务**。`week2/api/main.py`，FastAPI 0.141.1 + uvicorn 0.52.1（已装进 `week1/venv`）。
> 规则 8 交代：**FastAPI 是真手写的工程技能**，不是练手。和 Day 3 切块（已被 LangChain splitter 取代）正相反。

### 一句话

**脚本和服务的区别不是「能不能远程跑」，是输入的边界没了。**
脚本里 `PDF_PATH` 是你自己放的；服务的门一开，你所有「我知道输入长什么样」的假设全部作废。

> 推论：day2 那两个遗留（`#大小合理` 没真写、`finish_reason` 只 print）在脚本里是小毛病，
> **在服务里是事故**——脚本崩了只有你看见，服务里用户拿到半截总结还以为是成品。

### 一个接口 = 路径 + 方法 + 契约

契约是重点：**它是你和调用方之间唯一的协议**。
「先定形状，再验形状」——和 Week 2 后面的**结构化输出**是同一个思想，区别只是那个约束模型、这个约束调用方。

### 两条安全铁律 ⭐

1. **永远不要让客户端决定服务器去读哪个文件**（选 C「送路径」= 路径穿越漏洞，`../../.env` 直接读走 API key）
2. **不要相信客户端说的任何话**——文件后缀、`content_type` 都能伪造。看 `data.startswith(b"%PDF-")` 才是看真的

### 状态码：4xx 是调用方的错，5xx 是我的错

| 码 | 含义 | 这里对应 |
|---|---|---|
| 400 | 你给的东西不对 | 不是 PDF / 提取不出文字（扫描件） |
| 413 | **你给的太大了** | 文件超 10 MB / 正文超 20 万字符 |
| 429 | 你太快了 | Day 5 限流 |
| 500 | 我这边炸了 | 自己代码的 bug |
| 502 / 504 | 上游炸了 / 超时 | DeepSeek 挂了或不回话 |

**选错码，对方的重试逻辑就会做错事**：4xx 重试一万次还是错，5xx 重试才有意义。
⚠️ `422` 别自己用——FastAPI 已拿它表示 pydantic 校验失败。

### 「大」有两种，不是一回事 ⭐

| | 防什么 | 在哪查 |
|---|---|---|
| 文件字节数大 | CPU / 内存 / 上传耗时 | 提取**之前** |
| 提取出的文本长 | **烧钱 + 超窗口** | 提取**之后** |

两者没有对应关系：50 MB 扫描件可能提取出 **0 字符**；500 KB 纯文本 PDF 可能有 **100 万字符**。
**day2 那颗雷指的是第二种**——喂给模型的是文本，不是文件。

### 检查顺序：便宜的在前，贵的在后

```
判断 5 个字节 → 判断长度 → 【解析 PDF：吃 CPU】 → 判断文本 → 【调 API：20 秒 + 花钱】
```

一个 `.exe` 改名进来，第一行就被弹回去，零资源浪费。

### `not text.strip()` 而不是 `not text`

提取失败可能返回 `"\n\n\n\n"`——非空，但没内容。**这是「`or ""` 防不住 `''`」的同一个坑第三次换皮。**
判断「有没有东西」时，**存在 ≠ 有内容**。

### 契约里只放调用方需要的

`day2_summary.json` 那 5 个字段是**给自己存档**的，响应字段是**给前端显示**的，用途变了字段就得变。
筛选方法：对每个字段问「**前端拿它干什么**」，答不出就砍。

- **砍 `diff`（误差率）**——那是你校准估算系数用的，用户看到「估高了 17%」不知道该干什么。**它属于日志，不属于响应**
- **加 `truncated: bool`**——`finish_reason == "length"` 的出口。只在服务端 print，这句话**传不出去**
- **加 `model`**——换模型后质量变化能对上账

### `truncated` vs 报错（4.3 的默认选择，规则 7：跑完可改）

钱已经花了，这时报 5xx 扔掉结果是**纯损失**。选「照常返回 + 标记不完整」，
但**必须让调用方知道**，否则就成了静默 bug（本周重点短板）。

### `/health` 的用途：排除配置类故障，不花一分钱

```python
{"status": "ok", "model": MODEL,
 "api_key_configured": bool(os.getenv("DEEPSEEK_API_KEY")), "version": app.version}
```

**进程活着 ≠ 服务能用**。key 没配、模型名拼错、部署的是旧代码——进程全都好好的。
`bool()` 一层把「值」压成「是非」：`/health` 是公开的门，**key 一个字符都不能漏**（前 4 位也不行）。

| `api_key_configured: false` | **`.env` 没跟着部署上去**（部署到新机器最常见的事故） |
| `model` / `version` 不对 | 部署的是旧代码，push 了没重启 |

## Day 4 速查（教练给的硬知识，2026-08-06）

> 主题：**前端怎么把一个后端接口用起来**。`week2/api/static/index.html`，原生 HTML + fetch，零框架。
> 规则 8 交代：**手搓 fetch + 三态机是练手**，2026 年实际项目用 Axios + TanStack Query
> （`useQuery` 直接给 `isLoading` / `isError` / `data`，下面三态机那一整节它替你做了）。
> Week 3 用 Vue 重写时就换掉。**但手搓一次是必要的**——不知道它替你做了什么，就不知道它没做什么。

### `index.html` 和 `main.py` 什么关系

两个文件之间**没有 import、没有引用**，靠 **HTTP + 一份字段契约**连起来，跑在同一个 uvicorn 进程里：

```
浏览器开 /                    → app.mount("/", StaticFiles(html=True)) 吐出 index.html
点按钮 fetch("/summarize")    → 打回同一个服务的 @app.post("/summarize")
后端 return SummarizeResponse → FastAPI 序列化成 JSON
前端 await res.json()         → 拿到 {summary, truncated, input_tokens, output_tokens, cost, model}
```

**前端认识的只有那 6 个字段名。** 后端改一个字段名前端就白屏——这就是 Day 3 说的「契约」。
⚠️ `app.mount("/")` 必须写在所有路由之后，否则 `/summarize` 会先被这张网捞走（`main.py` 末尾注释）。

### fetch 的三条路径 ⭐ 今天最大的认知点

| 情况 | Promise | `res.ok` | 在哪处理 |
|---|---|---|---|
| 网络断 / DNS 挂 / CORS 拦 | **reject** | — | `catch` |
| HTTP 400 / 413 / 422 / 500 | **resolve** | `false` | `if (!res.ok)` |
| HTTP 200 | resolve | `true` | 正常渲染 |

**中间那行所有人第一次都会踩**：`fetch` 只在**网络层失败**时 reject。
服务器明明白白回了个 500，对 `fetch` 来说「消息送达了」= 成功。
**只写 `.catch` 不写 `res.ok`，所有 4xx/5xx 都会被当成功走下去。**

### 上传文件：FormData 三条

1. 字段名必须和后端参数名对上 —— `fd.append("file", f)` ↔ `async def summarize(file: UploadFile = File(...))`
2. **不要手写 `Content-Type`** —— multipart 的 header 带一个随机 boundary，浏览器自己生成。
   手写 `"multipart/form-data"` 会把 boundary 抹掉 → 后端解析不出字段 → **422**
3. `body: fd` 直接给，不要 `JSON.stringify`

### UI 三态机：每条出口都必须终结在某个状态

```
idle ─→ loading ─┬─→ done   (2xx，render(data))
                 ├─→ error  (res.ok === false → handleErrorResponse)
                 └─→ error  (catch，网络层挂了)
```

**判据：从 `setState("loading")` 往下数，有几条出口，就该有几次 setState。**
少一次 = 那条路径上界面永远转圈。今天真踩到两次：

- `handleErrorResponse` 算完 `msg` 忘了调 `setState` → 错误算对了，但没人显示
- `catch` 写成空块 `{}` → 网络挂了界面装死

另：`setState` 内部要**先归零**（清掉上一轮的错误/结果/警告）再施加新状态。

### `data.detail` 是什么、形状不固定 ⚠️

来源链：后端 `raise HTTPException(detail=X)` → FastAPI 包成 `{"detail": X}` → 前端 `await res.json()`。

| 码 | `detail` 类型 | 实测值 |
|---|---|---|
| 400 / 413 | **字符串**（自己写的） | `"上传的文件不是 PDF"` |
| 422 | **数组**（pydantic 生成） | `[{"type":"missing","loc":["body","file"],"msg":"Field required","input":null}]` |
| 500 | 字符串 `"Internal Server Error"` | **自己的 detail 传不出来** |

**直接 `textContent = data.detail`，422 会显示 `[object Object]`。**
所以 422 自己写一句人话，原始 detail 丢进 `console.log` 给开发者。

### 错误信息有两个受众 ⭐

| 给谁 | 走哪条路 | 写什么 |
|---|---|---|
| **用户** | `msg` → `setState` → `textContent` | 他下一步能做的事：「请换一个文件」「请稍后重试」 |
| **开发者** | `console.error(...)` | 原始 detail、状态码、栈——用户看不见也不需要看见 |

判据：**这句话说完，用户知道该干什么吗？** 答不出 = 不该给用户。
`Internal Server Error` 对用户是废话，对你是线索。

### 413 不能自己拼话

前端原本写「文件 X MB 超过 10 MB」。但后端 413 有**两种**原因（文件字节数超 / 正文字符数超）。
上传一个 2 MB 但正文 30 万字符的 PDF → 前端会说「2 MB 超过 10 MB」，**自相矛盾**。
**谁知道原因谁说话**：后端 `detail` 已经写清楚了，前端照搬。

### `textContent` 不是 `innerHTML`

`summary` 是**模型读了用户上传的 PDF** 之后吐出来的。
PDF 里可以塞 `<img src=x onerror=...>`，模型可能原样带出来。
`innerHTML` = 让别人的文件在你的页面上执行脚本。**`textContent` 把标签当字符显示，天然免疫。**

### `switch` 贯穿（fall-through）

```js
case 400:      // 故意不写 break，直接掉进下一个 case
case 413:
  msg = data.detail;
  break;
```

「这两个码处理方式一样」时用它。**这是唯一一个「漏写 break」反而正确的场合**，其余全是 bug。

### 静默 bug 的五张脸（本周主线 · Day 4 实物版）

| # | 长相 | 今天的实例 |
|---|---|---|
| 1 | 永远转圈 | `catch` 是空块 |
| 2 | 永远转圈 | `handleErrorResponse` 算完不 `setState` |
| 3 | **成功了却显示失败** | `data.cost.$toFixed(4)` 多打一个 `$` → 渲染时 TypeError → 掉进 catch |
| 4 | 异常被界面巧合掩盖 | `.name` 少了 `?.`，靠 `undefined > number === false` 恰好绕过去 |
| 5 | **说谎** | 缺 `else`：上一次的截断警告留在页面上，这次没截断也还显示 |

**第 3 条最贵：API 已经调了，钱已经花了**，用户看到「失败」，还会再点一次。
第 4 条的教训单列：`?.` 加在了报错那一行，没加在出问题的那一行——
**修在报错的地方 ≠ 修在出问题的地方**。正解是入口处 `if (!file) return`（C 段自己已经用过这手）。

### Python / 环境踩坑（Day 1 现场踩的）

| 坑 | 结论 |
|---|---|
| 脚本跑通了但屏幕空白 | **脚本模式下，算完就扔。想看什么就必须 `print` 什么**。`>>>` 交互模式才会自动显示 |
| `>>>` 里敲文件路径报 NameError | `$` 后面敲 **shell 命令**，`>>>` 后面敲 **Python 代码**，两个世界。退出 `>>>` 用 `exit()` 或 Ctrl+D（不是 Ctrl+C） |
| `FileNotFoundError` | 相对路径相对的是**执行命令时所在的目录（cwd）**，不是脚本文件的位置 |
| 装了包却 import 不到 | venv 跨机器同步 → `bin/python` 符号链接指向各自机器的 python，版本不同 → 两套 site-packages 互不可见 |

5. **prompt 里写"不超过 50 字"，模型可以完全不听**（实测块摘要 31~50 字不等）
   → 同理，**prompt 里的"请返回 JSON"也是请求不是命令**，硬手段只有 `response_format`

## 教练自查（Day 2 · 2026-07-29）

> Claude Code 这一天犯的错，全部记在这。写进来的理由不是认错，是**这些错和 ly 正在学的东西是同一批**——

### ① 量纲错配 —— 我批评的错，我自己犯了 ⭐ 最严重

拿 `completion_tokens ÷ 正式回答字符数` 算出「中文输出实测 0.916」，据此宣称「官方 0.6 严重低估」。

**分子含 `reasoning_tokens`（175，占 48%），分母只有正式回答的字符。分子分母不是同一件事。**
剔掉推理后真实值是 **0.55**，官方 0.6 基本准确。

**连带损害**：
- 让 ly 把假数据（0.916）写进了速查表
- Q2 点评里据此批评 ly「用 0.6 是低估」——**批评本身是错的**，事后把 Q2 从 0.5 改判 0.8，总分 2.2 → 2.5

**教训**：**量纲错配不会报错。** 两个数都是正数、单位看起来都是「token/字符」、算出来的值也在合理范围内——
唯一能拦住它的动作是**开口前先问一句「这两个数说的是同一件事吗」**。
这正是 report() 里那条误差率反复讲了三轮的东西，讲的人自己没做到。

### ② 出题时把答案摆在同一屏

在 review 里完整列了 4 个静默 bug，紧接着让 ly「不看 review 自己找出来」。

**教训**：一个实验，如果两个相反的前提（真懂 / 抄的）会产生**完全相同的观测结果**，
那这个实验的信息量是 **0**。不是「结果不理想」，是**根本测不到东西**。
出题前先问：**答对和抄对，我分得出来吗？**

### ③ 确认偏误 —— 据弱信号判定 ly 抄答案

依据只有「答案是标签、没有解释」这一条弱信号（「懂了但懒得写」同样解释得通）。
而手上有**两条反向证据一条都没用**：

- ly 贴的三行源码含 `if / continue`，那两行我从没引用过 → 指向他在读源文件
- ly 多答了一条不在我清单里的（`min(240,500)`）→ 抄清单不会多出这条

**根因**：出题当下就知道泄题了，「这题废了」的结论**在看到答案之前就定了**，
之后只挑支持它的信号看。

**教训**：**先有结论，证据就沦为装饰。** 判断顺序反了，能力再强也没用。

### ④ 描述机制前没跑真实数据

断言页间粘连是「上一页最后一个词 + 下一页第一个词」。
实测发现是**页码夹在中间**：`...the sequence\n6length n is smaller...`，
把 `sequence length` 这个核心术语劈成了 `sequence` 和 `6length`。

**教训**：机制靠推理能推个大概，**细节必须实测**。而 bug 往往就藏在细节里。

### ⑤ 推荐 `.6f` 没考虑值域

建议用 `.6f` 显示成本，没算成本的量级跨度。**1 token 时 `.6f` 显示 `0.000000`**——
和 ly 上一版 `.2f` 显示 `0.00` 是同一个病，只是阈值往下挪了 4 位。
（ly 质疑「谁知道小数点停在哪」之后才发现，改推 `.6g`。）

**教训**：给格式化建议前先问**这个值可能有多大、多小**。跨数量级的量不能用固定小数位。

### ⑥ 两处表述不严谨

- Q2 说「用昨天实测的比例」，但实测的两个值（英文输入 / 中英混合输出）对**纯中文小说**都不直接适用，题目本身有歧义
