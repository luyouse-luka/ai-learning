### Day 1 · 2026-08-12 · JSON 解析

**今天学到的最关键 1 件事**：
查看json.loads失败的样子，并写一个字段效验的函数（作用是safe__parse挡不住的那一层）,而safe__parse只判断json是否合法，只会分别调用两次不同的max_tokens限制查看结果
**最难的点 / 卡了多久**：
1. 没懂safe_parse，validate，demo_offline到底什么有什么意义----
      1. safe_parse 是解析判断json合不合法，比如json内部格式不合法，内容缺少双引号，内容单引号，多逗号少引号等；空字符串；模型吐出垃圾内容，开头出现中文，因为 JSON 必须从 { 或 [ 开始。
      2. validate 是检查类型效验字段的函数，检查有没有缺少字段，字段类型对不对，比如当safa_parse都成功放行，但字段缺失 {"title": "x"}，类型不符{"count": "42"}等
      3. demo_offline 是查看三条坏的输入情况，打印出的结果，1 json不合法 2. 字段类型不合法，3. json不合法 
2. 语法问题， isinstance  判断一个对象是不是某种类型，not isinstance 当字段不是对应的类型时走这个分支，
      expected_type.__name__ 获取期望类型的名字
      type(data[field]).__name__ 获取实际值的类型名字
      problems = validate(data, {"title": str, "count": int}) if data is not None else ["Parsing failed"] 这是一个三元条件判断的一个写法
3. 今天的流程是先写json解析函数以及validate。运行demo_offline 查看一些异常情况进行分析，然后再运行api的调用，查看data在经过解析之后是否会抛出异常

第 2 层：字段在不在、类型对不对 → validate 管
第 3 层：值有没有意义 → 没人管（业务规则）

| 场景 | 浏览器端结果 |
|---|---|
| `fetch('http://127.0.0.1:8913/...')` 跨源打探针服务器 | `THREW TypeError: Failed to fetch` |
| `fetch('http://127.0.0.1:8000/health')` 跨源打后端 | `THREW TypeError: Failed to fetch` |
| `fetch('/api/health')` 同源走代理 | `RESOLVED status=200` + 正确 JSON |

**关键证据**（探针服务器自己的收件日志，同一次浏览器请求）：

```
浏览器发的：HIT path=/from-browser Origin=http://localhost:5174 UA=Mozilla/5.0 (X11; Ubuntu...)
curl  发的：HIT path=/selftest     Origin=None                  UA=curl/7.81.0
```

**结论一：跨域「失败」的请求，在服务器那一侧是成功的。**
请求真的发出、服务器真的收到并返回 200，是浏览器拿到响应后发现没有
`Access-Control-Allow-Origin`，**把已经到手的响应扔掉**，才给 JS 抛 `TypeError`。
数据被扣在浏览器里，不是被挡在服务器外。推论：**跨域不是安全防护**，
curl / Postman / 别的服务器照拿；它拦的只是「别人网站用你的登录态偷读你的数据」。

**结论二：`Origin=None` 说明 curl 连这个请求头都不发** —— 它没有「源」这个概念，
所以同源策略对它完全不作用。这就是「curl 直连 8000 不报错」的真正原因，
**不是因为同源，是因为没人管它。**

> 不能互相赋值**。`?? null` 不是"保险起见"，是把 undefined 翻译成 null 的**类型转换**。
>
> **丢分形状**：两处都不是不会，是**不够精确**——Q1 机制对词错，Q3 方向对只说一边。
